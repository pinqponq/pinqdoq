# pinqloq Task Runner — implementing a task (step 5)

Read this file in full right after `locks.py claim` (or `locks.py lock`) gave you a task. It is part of SKILL.md; the trust rules, Non-Goals and stop conditions there still apply.

## PR gate (check before every `gh pr create`, and before reporting a task as done)
Open the PR only when **all** of these hold; otherwise push the branch, keep the task `in_progress` / `verification_blocked`, keep the card **In progress**, and say what is missing in the run report:
- [ ] The task has **no open question** (`open_questions` empty; only older tasks can still have one). (2026-10-03: pinqloq#128 opened PR #129 with S19 open.)
- [ ] **PIT ≥ 85%** on changed lines (web projects: StrykerJS, .NET: Stryker.NET, same threshold), every survivor explained (step 3.6). A score under the threshold is a blocker: raise it (more tests) before opening the PR; a decision about it does not lift the gate. (2026-10-03: rindle-cmp#381 opened PR #398 at 45% while asking S20.)
- [ ] Tests, device evidence and pinqloq before/after are in place (step 12).
- [ ] `pinq_code-review` on the full branch is clean (step 8).
- [ ] **No duplicate of open work.** Before adding infrastructure the task did not ask for (a test project, CI change, shared helper, package), check the repo's open PRs and branches (`gh pr list -R <repo> --state open`) for the same thing. If one exists, build on it (branch from it, PR base = its branch) instead of opening a parallel one. (2026-10-04: pinqloq#117 opened mcp-server#10, a second test project, while #7 already added one.)
- [ ] **Moves and replacements follow this order.** When the task moves code to a shared library or replaces a whole layer, first open the characterization tests as their own PR against the default branch (they must pass there without any of the new code; the testing standard is "Moving or Replacing Existing Code" in `rules/common.md`), then base the moving branch on that PR and run the whole suite. In the moving PR's description, list each removed piece, whether it had a test before and which test covers it now, and list any behavior change the new library makes possible with what changes, why it helps and which clients it can affect.

## Auto-merge rubric (every PR's "Notlar")
The orchestrator (the Claude Code session the owner chats with, pinqponq/pinq-orchestrator) merges a runner PR on its own only when the PR note says every gate passed and the risk is low. Write both into "Notlar" of every PR the runner opens or updates, repos outside the pinqponq org (e.g. atakancelik/GlobalOtoparkPanel) and version bumps in consumer repos included.

**Gates** (all required; list each as ✅ or ❌ with one short reason when ❌):
- Not draft; mergeable and clean (blocked only by the required-review policy is fine: admin merge is allowed then).
- CI green (or "CI yok" when the repo has no workflow).
- Tests for every changed behavior.
- PIT / Stryker at the threshold, every survivor explained.
- `pinq_code-review` on `origin/<default-branch>...HEAD` is clean (no open findings).
- Device proof for UI / Android work (or "UI değişikliği yok").
- Shared-code PR: the consumers' composite-build proof is in place first.
- Stacked PR: its base branch is already merged.
- No decision waits for the owner (no `❓` decision).

**Risk:** `düşük` or `düşük değil: <reason>`. It is not low when the change:
- touches authentication, authorization, payments, secrets, data migration, production config or security;
- changes a shared library or a contract that every consumer uses;
- has missing or `FLAKY` evidence;
- is a wide change across several modules.
There is no line-count limit.

**Never automatic**, whatever the risk: publishing (Maven, NuGet), Portainer or production deployment, and anything the owner said he will review himself. Say so in the note ("otomatik merge yok: <reason>").

**Who merges:** the runner that did the task decides and merges, at the end of its own run, after step 11. When every gate is ✅, the risk is `düşük` and nothing is "never automatic": `gh pr merge <n> --squash` (add `--admin` only when the required-review policy is the sole blocker; use `GH_TOKEN=$(gh auth token --user pinq-ponq)` for Atakan's repos), wait for the merge, move the card to Done, and write "Otomatik merge edildi" with the gates and risk line in the run report and as a PR comment. When any gate fails, the risk is not low or the PR is never-automatic, do not merge: leave the PR open with the risk line in "Notlar" for the owner. A stacked or consumer PR that is bound by a composite waits for its shared release. After merging, check that CI on the base branch stays green; if it breaks, revert the merge and report it in "İnsan gerekiyor". The chat session does not re-evaluate runner PRs.

Note format in "Notlar":
```
Otomatik merge: kapılar ✅ taslak değil · ✅ CI · ✅ testler · ✅ PIT · ✅ pinq_code-review · ✅ cihaz · ✅ paylaşılan kod · ✅ taban · ✅ karar
Risk: düşük
```

## Verification retries
Tasks in `verification_blocked` are retried only in the pinqloq verification step: if pinqloq is reachable again, run the device scenario and log checks, update the PR's pinqloq sections and continue from step 11; otherwise leave them as they are. `preflight.py` does not report a retry while the task's `backend_pr` is still open; it reports the task again when that pull request is merged.

## Handoff file (one per task, since 2026-10-07)

A task often spans several sessions (questions, change requests, retries). Each later session must continue from what the earlier ones knew, not re-explore. `scripts/handoff.py` keeps one file per task in `~/.claude/pinqloq-task-runner/handoffs/` (outside every worktree, never committed).
- **Start:** right after claiming or locking a task, before reading code: `python3 scripts/handoff.py show <task key>`. Trust it as the starting point: open the files at the `file:line` it names, do not re-derive its decisions, start from its "Next steps". Re-read code only where the handoff is silent or the branch moved since (`git log` after its `Updated` time).
- **During:** add a bullet the moment something worth keeping happens, chained into a command you run anyway: `python3 scripts/handoff.py note <task key> decisions "<decision> — why: <reason>"` (also `files "<path:line> — changed|read: <note>"`, `verified "<what ran, result>"`, `assumed "<…>"`, `questions "S27: …"`). One line each; no transcripts, no file bodies, no secrets or test-account values.
- **Every exit** (decision taken, PR opened or updated, change request done, stop condition, end of run): replace `state`, `next` and `resume` with `printf '…' | python3 scripts/handoff.py set <task key> <section>`: where it stands, the ordered next steps, and the exact commands to get back (worktree, branch, composite-build or device setup, the test command). A reader must be able to continue from the file alone.
- When an answer or review arrives, the session that consumes it adds it under `decisions` (answer + what it changes) before working on it.

## Delegate noisy steps to subagents (context budget)
Every turn re-reads the whole session context, so long Gradle/Maestro/PIT output and screenshots in the runner's own context multiply the cost of the rest of the task (2026-10-05: the #402 session grew to 454k context and 120M cache-read tokens over 424 turns). Run these steps through the `Agent` tool with the named `subagent_type` and keep only the subagent's short reply:
- **`pin-test`** — every build, test run, Roborazzi verify/record, PIT (`run_pit.py`), StrykerJS (`run_stryker_js.py`), `dotnet build`/`dotnet test`/Stryker.NET and develop baselines. Pass: worktree, task key, lock key, exact commands.
- **`pin-device`** — every Maestro flow run (old build and task build, Android and iOS), screenshot inspection, and the pinqloq queries for a run window. Pass: worktree, task key, lock key, your session name (and which device locks you hold), platform, build to install, flows, accounts and how the couple must end, the pinqloq queries, and whether it may edit flow YAML.
- **`pin-review`** — `pinq_code-review` on `origin/<default-branch>...HEAD` (step 8). Pass: worktree, task key, default branch, task scope.

Rules:
- You still own the decisions: fix the code yourself from the reply, rerun through the subagent, and write the PR/report from its summaries and evidence paths. Do not re-read its log files or screenshots in full; open a single log excerpt (`grep`/`tail -n 40`) or one screenshot only when the reply is not enough to decide the fix.
- Each subagent reply includes step durations; add them to the run's `runs.log` line (e.g. `pin-test 6m, pin-device 14m, pin-review 3m`) so slow steps become visible. Builds, tests, PIT and Maestro runs through `run_build.py`/`run_pit.py` are also recorded in `~/.claude/pinqloq-task-runner/timings.jsonl`; append the output of `python3 scripts/timing_report.py --task <key> --brief` to the same line (time per build/test/pit/device, failed runs, flow retries).
- Builds and tests always go through `scripts/run_build.py --cwd <worktree> --lock <key> -- <command>` (full output to `build/runner-logs/`, short summary to stdout), also when you run one yourself. Screenshots are read only as reduced copies from `scripts/shrink_images.py` (800 px JPEG), never at full resolution; the originals stay the PR evidence.
- Never write `rm` with a command substitution or variable target (`rm -rf "$(ls -td …)"`, `rm -rf $W/…`): Claude Code stops for approval on those even in bypass mode and the unattended run hangs. Delete build output with `scripts/clean_build_output.py --cwd <worktree> <relative paths>` (or `--newest '<glob>'`); it only deletes inside `build/` or `_small/`. A literal relative `rm -rf build/…` is fine.
- Run directly, without a subagent, only short commands whose output you need verbatim (git, gh, `locks.py`, `state_tx.py`, `board.py`, `report.py`, a single compile check you expect to pass, `ls`/`grep`).
- Acquire and release the device locks yourself (step 7, per platform, `--couple` for shared-state flows); tell pin-device which locks you hold; the subagent only touches them. While pin-device runs one platform, another session may use the other device. Write the device-run window and pinqloq tables it returns into the PR as they are.
- If the `Agent` tool is unavailable or a subagent returns `ERROR` twice for the same step, run the step directly, send its output to a log file (`cmd > build/runner-logs/<step>.log 2>&1`) and read only `tail`/`grep` of it; note "subagent kullanılamadı" in `runs.log`.
- Independent steps may run in parallel subagents (e.g. `pin-test` for desktop tests while `pin-review` reviews), never two `pin-device` at once.

## Steps
1. **Locate repo:** `<workspace_dir>/<repo>` if its `origin` resolves (`gh repo view <origin> --json nameWithOwner`) to `pinqponq/<repo>`; otherwise `gh repo clone pinqponq/<repo> <workspace_dir>/pinqponq/<repo>`.
2. **Isolate:** never touch the user's checkout's working tree. `git fetch origin` then `git worktree add <workspace_dir>/.task-runner-worktrees/<repo>-<n> -b task/<n>-<slug> origin/<default-branch>` (default branch from `gh repo view --json defaultBranchRef`). Reuse the worktree on later runs.
3. **Absorb pinq-doq (mandatory, before writing any code — the team requires full compliance).**

Installed means these are committed in the repo: the `.pinq-doq/` submodule, the rules in `.claude/rules/`, the skills in `.claude/skills/`, the `.claude/.pinq-doq-version` stamp, and a `CLAUDE.md` that points to them. Before any other work, check it in the worktree root: `grep -qs 'path = .pinq-doq' .gitmodules && test -f .claude/rules/common.md && test -f .claude/.pinq-doq-version && test -d .claude/skills && grep -qs pinq-doq CLAUDE.md && echo pinq-doq-ok || echo pinq-doq-missing`. On `pinq-doq-missing`, install pinq-doq right away. The install is the first commit of the task's first PR in that repo. Pull the canonical clone first (`git -C ~/StudioProjects/pinqdoq pull --ff-only`), then:
      - `.gitmodules` has no pinq-doq entry: follow `~/StudioProjects/pinqdoq/tasks/integrate.md`.
      - `.gitmodules` already has one (at `.pinq-doq` or at the old `.claude/rules`): run step 3.2 (submodule init) when the path is `.pinq-doq`, then follow `~/StudioProjects/pinqdoq/tasks/update.md`; it converts the old layout and copies the rules and skills again. When `CLAUDE.md` still has no pointer, add the block from `integrate.md` step 3.
      A task that creates a repo also installs pinq-doq in the first commit of that repo's first PR.
   2. When the repo has a `.pinq-doq` submodule, run `git submodule update --init .pinq-doq` in the worktree (checkouts on this Mac have it uninitialized, so `.pinq-doq/scripts` and `.pinq-doq/references` are otherwise empty).
   3. Read **in full**: `rules/common.md` and every stack rule for the files you will touch (Kotlin: `kotlin-architecture.md`, `kotlin-naming.md`, `kotlin-conventions.md`, `kotlin-deveng-core.md` when deveng-core-kmp is a dependency; .NET: `dotnet-conventions.md`), plus the repo's own `CLAUDE.md`/`AGENTS.md`. Then read the deep references relevant to the change (`references/kotlin/*.md`, e.g. mvi-pattern, data-layer, viewmodel-patterns, error-handling, deveng-core-reference for UI).

To learn a component's API, read `references/kotlin/deveng-core-reference.md` first, then the library's source with `git -C ~/StudioProjects/<repo> fetch -q && git -C ~/StudioProjects/<repo> grep -n <Name> origin/<default-branch>` / `git show origin/<default-branch>:<path>` (never check out or edit the user's clone). Never unzip jars or read the Gradle cache for our own libraries (2026-10-07: a #401 run spent 3 calls unzipping the core jar for `CustomDialog`).
   4. Use the pinq-doq skills and their scripts for every step they cover (`pinq_add-feature` → `pinq_presentation-scaffold` / `pinq_api-endpoint-integration`, `pinq_kmp-theme-setup`); write code by hand only where no script applies, and say why in the PR.
   5. **Testing is part of the task, not an extra.** Read `rules/kotlin-testing.md` and `references/kotlin/testing.md` in full (merged in pinqponq/pinqdoq#19; if the repo's `.pinq-doq` submodule predates it, read them from `~/StudioProjects/pinqdoq` on `main`), plus the repo's CLAUDE.md "Testing" section, and apply Google's `testing-setup` skill principles (`~/.claude/skills/testing-setup`) as translated there. **Scope tests to the task — apply the MUST rules, not every SHOULD.** Every task adds/updates tests for the logic it changes (bug fix → a test that fails without the fix) and the UI behavior test for the interaction it changes. Screenshot tests only when the task changes how something looks, and only for the state it changes. Do **not** add extras the task does not need: large-font / `fontScale` variants, multiple window sizes, screenshots of unchanged components, test infrastructure or fakes for code the task does not touch. A SHOULD from `kotlin-testing.md` is added only when the task itself is about it (e.g. a new screen, an accessibility/font issue). 2026-10-01 incident: #377 (a delete race) added `preparing_dialog_*_large_font` and media-export screenshots; the team called them unnecessary scope. The PR lists the tests added and the exact commands run with their results.
   6. **Mutation testing is mandatory (PIT, diff-scoped).** After the tests pass and before `pinq_code-review`, run `python3 scripts/run_pit.py <worktree> origin/<default-branch>` (JVM/desktop tests; jars download to `~/.cache/pinq-pit` on first run; ~1 min). Rule text: `kotlin-testing.md` → "Tests must be able to fail". Score on changed lines must be **≥ 85%**; below it, add or sharpen tests for the survivors and rerun. Every remaining survivor goes into the PR's "Testler" section with a one-line reason (screenshot/device flow covers it, unreachable defensive path, equivalent/redundant code); a survivor on the core guard or branch the task introduces is never acceptable. A redundant call PIT exposes is removed or tested. Never widen the script's ignore list to raise the score. **Web projects (TypeScript/JavaScript) use StrykerJS instead:** `python3 scripts/run_stryker_js.py <worktree> origin/<default-branch> [--project <folder with package.json>]` through `pin-test` (rule: `rules/web-testing.md` → "Mutation testing"; setup: `references/web/e2e-playwright.md` § 8). It mutates only the changed production files, counts the changed lines, leaves out `CompileError`/`RuntimeError`/`Ignored` mutants as `ignored_noise`, writes the full output to `build/runner-logs/` and prints the same score, killed, total, ignored_noise, threshold and survivors fields as `run_pit.py` (exit 1 under the threshold, 2 when git or Stryker could not run, the config is missing or the report misses a changed file). Reruns reuse `build/stryker/incremental.json` the way PIT reuses `build/pit-history`. Same threshold and same rules as PIT: below 85% add tests or explain every survivor in the PR, never ask the owner. A web project without `stryker.config.mjs` gets the setup in the same PR. Kotlin keeps PIT, .NET keeps Stryker.NET. A repo with no PIT, StrykerJS or Stryker.NET setup: say so in the PR instead of skipping silently. Rerun after every change request that touches tests or logic (reruns reuse `build/pit-history`, so they only re-test mutants whose class or covering tests changed; scores equal a full run). While adding tests for survivors, ask `pin-test` for filtered test runs of the affected classes; the full suite stays the gate before PIT/review and after any later production change.
   7. **Test infrastructure:** rindle-cmp has it on `develop` (pinqponq/rindle-cmp#385). In a repo without test infrastructure, set it up first following `references/kotlin/testing.md` as its own PR and mention it in the run report.
   7b. **Core additions ship with a sample and docs (deveng-core-kmp).** Any new or changed public component, API or SDUI capability in `deveng-core` is not done until the same PR also has: (a) a working example in `sample/composeApp` (a new demo screen reachable from the main list, or a section in an existing demo) showing each new public piece in its main states, built with `./gradlew :sample:composeApp:assembleDebug` and the desktop target; (b) the `README.MD` section updated or added (usage, a link to deeper docs); (c) a "Sample" line in the PR body naming the demo screen. Before `pin-review`, run `git diff --stat origin/<default-branch>...HEAD` and confirm `sample/` and `README.MD` are in it; `pin-review` reports a missing one as a blocking finding. Only a change with no public surface (internal refactor, bug fix) may skip the sample, and the PR says so. Never defer the sample to a later task; if it truly cannot be done now (needs a platform you cannot build), open a card for it in the same run and link it in the PR.
   8. **Comments follow `common.md` → "Comment Standards".** Default is no comment. Do not add KDoc/`/** */` or `//` comments that restate a name (e.g. a doc comment above a new `State` field like `isBulkDeleteProgressVisible`); before adding any comment, check whether the surrounding code has comments of that kind at all — if the file/feature has none, add none. A comment is allowed only for a verifiable business rule, external-system quirk, workaround (with tracking reference) or trade-off. 2026-10-01 incident: #377 added `/** A bulk delete is running; … */` above a State field; the team rejected it.
   9. **`pinq_code-review` runs on the whole branch, last, and its findings get fixed.** After all code for the run is done (including change requests), run `pinq_code-review` on the full diff `origin/<default-branch>...HEAD` — never only the last commit. Fix every Critical/Major **and every rule-backed Minor/Nit** in the changed lines (comments, naming, patterns); re-run until nothing rule-backed is left. Only findings outside the task's scope may stay, each listed with its reason. Put the final verdict (range reviewed, counts, what was fixed) in the PR under "pinq-doq uyumu".
4. Move the card to **In progress** with `python3 scripts/board.py move <task key> "In progress"` (never `gh project item-list`/`field-list`/`item-edit`, never hardcoded IDs), add the runner account as assignee (`gh issue edit <n> -R <repo> --add-assignee pinq-ponq`; existing assignees stay). Do not comment on the issue that work started: the card column and the assignee already show it, and every runner comment sends the assignees a GitHub notification. The runner comments on an issue only to report a result the team must read (e.g. a reproduction outcome that changes the plan) and to post the PR link; never progress notes such as "continuing with the recommended options".

   **Follow existing patterns; never introduce a new structural one on your own.** Before writing a fix, find how the same kind of problem is already solved in the repo (`grep` for it) and do it the same way. Examples:
   - Error handling: errors are distinguished in the **ViewModel** via `launch(notifyError = false, onError = { exception -> if (exception.cause is DevengUiError.<Type>) … else setError(exception) })` (see `LoginViewModel`). Services stay thin calls to `devengNetworkingModule.sendRequest`; repositories and use cases stay pass-through.
   - Never bypass `DevengNetworkingModule` (raw Ktor `httpClient.delete/get`, `buildRequestUrl`, `setupAllHeaders`, hand-decoding `ErrorResponse`), never add new exception types or error-mapping layers in data/domain, never add a new base class, wrapper or helper that has no precedent.
   If the existing pattern cannot express what the task needs (e.g. the library maps the status you need to a generic error), **do not invent a workaround silently**: weigh options A/B/(C), take the recommended one and record it as a decision (SKILL.md → "Decide, do not wait") — for example "A: ViewModel'de mevcut `DevengUiError` ile ayırt et (sınırlı), B: deveng-networking-kmp'ye 404 eşlemesi ekle (ayrı PR), C: ayırt etme, sadece çift isteği engelle". Any change with no precedent in the repo counts as a developer decision and is listed under "Alınan kararlar". 2026-10-01 incident: #377 replaced `sendRequest` with a raw Ktor call plus `GalleryMediaNotFoundException` in the service to detect 404 without saying so; the team rejected it — the check belonged in the ViewModel. ## No skipping without proof
The runner may not skip a required step on an assumption. In particular:
- **Device verification is mandatory for every UI-affecting task.** Boot the device, install the build, and run the issue's scenario as a Maestro flow on Android. Run it on iOS too only when the change touches an `expect`/`actual` pair or iOS-only code, or when there is a concrete reason to suspect iOS behaves differently; say in the PR which case applies. A web project runs the scenario as a Playwright proof run instead (step 7, web), also in an unattended session; only an expired sign-in without a fixed code or a missing `.env` is reported as `verification_blocked`, never skipped. "No iOS tap tool" is not a blocker: Maestro drives the simulator. "Needs login", "needs another account", "needs unpairing" are never blockers: sign in/out, unmatch and re-match with the test accounts (step 7). "Needs data / needs a real device" may be claimed only after actually trying, and only with evidence attached (the screenshot of the blocking screen plus the command output). A blocker claimed without such evidence is a runner error.
- **Required tests are not optional.** If a MUST test from `kotlin-testing.md` looks hard (deep constructor graphs, concrete collaborators), creating the seam (an interface with a Default implementation, a fake, a test helper) is part of the task. Skipping is allowed only when the rule itself exempts the code, never because it is laborious.
- **pinqloq verification is not optional.** A task is not done until pinqloq logs confirm it (step 7) and the PR shows the before/after log comparison. A passing unit test, a screenshot, or "pinqloq was unreachable" is not a substitute; an unreachable pinqloq is reported as a blocker with the exact error, never silently skipped.
- **Code review covers the whole branch.** A review of only the last commit does not count; the PR's "pinq-doq uyumu" must name the reviewed range `origin/<default-branch>...HEAD`.
- **No unprecedented structure.** Before step 10, diff the change against `origin/<default-branch>` and list every new class, layer, library bypass or error-handling approach that has no existing counterpart in the repo; each one must either be removed (use the existing pattern) or be listed under "Alınan kararlar" with why the existing pattern was not enough. Say so in the PR under "pinq-doq uyumu".
- Before adding the run report, self-check each task against this list; any unmet item keeps the task `in_progress` for the next run instead of being reported as done.
