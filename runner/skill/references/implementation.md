# pinqloq Task Runner — implementing a task (step 5)

Read this file in full right after `locks.py claim` (or `locks.py lock`) gave you a task. It is part of SKILL.md; the trust rules, Non-Goals and stop conditions there still apply.

## PR gate (check before every `gh pr create`, and before reporting a task as done)
Open the PR only when **all** of these hold; otherwise push the branch, keep the task `in_progress` / `waiting_reply` / `verification_blocked`, keep the card **In progress**, and say what is missing in the run mail:
- [ ] The task has **no open question** (`open_questions` empty). A question asked in this run means no PR in this run. (2026-10-03: pinqloq#128 opened PR #129 with S19 open.)
- [ ] **PIT ≥ 85%** on changed lines, every survivor explained (step 3.6). A score under the threshold is a blocker even when you also asked about it; ask *and* wait. (2026-10-03: rindle-cmp#381 opened PR #398 at 45% while asking S20.)
- [ ] Tests, device evidence and pinqloq before/after are in place (step 12).
- [ ] `pinq_code-review` on the full branch is clean (step 8).
- [ ] **No duplicate of open work.** Before adding infrastructure the task did not ask for (a test project, CI change, shared helper, package), check the repo's open PRs and branches (`gh pr list -R <repo> --state open`) for the same thing. If one exists, build on it (branch from it, PR base = its branch) instead of opening a parallel one. (2026-10-04: pinqloq#117 opened mcp-server#10, a second test project, while #7 already added one.)

## Verification retries
Tasks in `verification_blocked` are retried only in the pinqloq verification step: if pinqloq is reachable again, run the device scenario and log checks, update the PR's pinqloq sections and continue from step 11; otherwise leave them as they are.

## Handoff file (one per task, since 2026-10-07)

A task often spans several sessions (questions, change requests, retries). Each later session must continue from what the earlier ones knew, not re-explore. `scripts/handoff.py` keeps one file per task in `~/.claude/pinqloq-task-runner/handoffs/` (outside every worktree, never committed).
- **Start:** right after claiming or locking a task, before reading code: `python3 scripts/handoff.py show <task key>`. Trust it as the starting point: open the files at the `file:line` it names, do not re-derive its decisions, start from its "Next steps". Re-read code only where the handoff is silent or the branch moved since (`git log` after its `Updated` time).
- **During:** add a bullet the moment something worth keeping happens, chained into a command you run anyway: `python3 scripts/handoff.py note <task key> decisions "<decision> — why: <reason>"` (also `files "<path:line> — changed|read: <note>"`, `verified "<what ran, result>"`, `assumed "<…>"`, `questions "S27: …"`). One line each; no transcripts, no file bodies, no secrets or test-account values.
- **Every exit** (question asked, PR opened or updated, change request done, stop condition, end of run): replace `state`, `next` and `resume` with `printf '…' | python3 scripts/handoff.py set <task key> <section>`: where it stands, the ordered next steps, and the exact commands to get back (worktree, branch, composite-build or device setup, the test command). A reader must be able to continue from the file alone.
- When an answer or review arrives, the session that consumes it adds it under `decisions` (answer + what it changes) before working on it.

## Delegate noisy steps to subagents (context budget)
Every turn re-reads the whole session context, so long Gradle/Maestro/PIT output and screenshots in the runner's own context multiply the cost of the rest of the task (2026-10-05: the #402 session grew to 454k context and 120M cache-read tokens over 424 turns). Run these steps through the `Agent` tool with the named `subagent_type` and keep only the subagent's short reply:
- **`pin-test`** — every build, test run, Roborazzi verify/record, PIT (`run_pit.py`), `dotnet build`/`dotnet test`/Stryker.NET and develop baselines. Pass: worktree, task key, lock key, exact commands.
- **`pin-device`** — every Maestro flow run (old build and task build, Android and iOS), screenshot inspection, and the pinqloq queries for a run window. Pass: worktree, task key, lock key, your session name (and which device locks you hold), platform, build to install, flows, accounts and how the couple must end, the pinqloq queries, and whether it may edit flow YAML.
- **`pin-review`** — `pinq_code-review` on `origin/<default-branch>...HEAD` (step 8). Pass: worktree, task key, default branch, task scope.

Rules:
- You still own the decisions: fix the code yourself from the reply, rerun through the subagent, and write the PR/mail from its summaries and evidence paths. Do not re-read its log files or screenshots in full; open a single log excerpt (`grep`/`tail -n 40`) or one screenshot only when the reply is not enough to decide the fix.
- Each subagent reply includes step durations; add them to the run's `runs.log` line (e.g. `pin-test 6m, pin-device 14m, pin-review 3m`) so slow steps become visible. Builds, tests, PIT and Maestro runs through `run_build.py`/`run_pit.py` are also recorded in `~/.claude/pinqloq-task-runner/timings.jsonl`; append the output of `python3 scripts/timing_report.py --task <key> --brief` to the same line (time per build/test/pit/device, failed runs, flow retries).
- Builds and tests always go through `scripts/run_build.py --cwd <worktree> --lock <key> -- <command>` (full output to `build/runner-logs/`, short summary to stdout), also when you run one yourself. Screenshots are read only as reduced copies from `scripts/shrink_images.py` (800 px JPEG), never at full resolution; the originals stay the PR evidence.
- Never write `rm` with a command substitution or variable target (`rm -rf "$(ls -td …)"`, `rm -rf $W/…`): Claude Code stops for approval on those even in bypass mode and the unattended run hangs. Delete build output with `scripts/clean_build_output.py --cwd <worktree> <relative paths>` (or `--newest '<glob>'`); it only deletes inside `build/` or `_small/`. A literal relative `rm -rf build/…` is fine.
- Run directly, without a subagent, only short commands whose output you need verbatim (git, gh, `locks.py`, `state_tx.py`, `board.py`, `mailer.py`, a single compile check you expect to pass, `ls`/`grep`).
- Acquire and release the device locks yourself (step 7, per platform, `--couple` for shared-state flows); tell pin-device which locks you hold; the subagent only touches them. While pin-device runs one platform, another session may use the other device. Write the device-run window and pinqloq tables it returns into the PR as they are.
- If the `Agent` tool is unavailable or a subagent returns `ERROR` twice for the same step, run the step directly, send its output to a log file (`cmd > build/runner-logs/<step>.log 2>&1`) and read only `tail`/`grep` of it; note "subagent kullanılamadı" in `runs.log`.
- Independent steps may run in parallel subagents (e.g. `pin-test` for desktop tests while `pin-review` reviews), never two `pin-device` at once.

## Steps
1. **Locate repo:** `<workspace_dir>/<repo>` if its `origin` resolves (`gh repo view <origin> --json nameWithOwner`) to `pinqponq/<repo>`; otherwise `gh repo clone pinqponq/<repo> <workspace_dir>/pinqponq/<repo>`.
2. **Isolate:** never touch the user's checkout's working tree. `git fetch origin` then `git worktree add <workspace_dir>/.task-runner-worktrees/<repo>-<n> -b task/<n>-<slug> origin/<default-branch>` (default branch from `gh repo view --json defaultBranchRef`). Reuse the worktree on later runs.
3. **Absorb pinq-doq (mandatory, before writing any code — the team requires full compliance).**
   1. In the worktree run `git submodule update --init .pinq-doq` when the repo has a `.pinq-doq` submodule (checkouts on this Mac have it uninitialized, so `.pinq-doq/scripts` and `.pinq-doq/references` are otherwise empty).
   2. Repos without pinq-doq (e.g. deveng-core-kmp, pinqops): use the canonical clone `~/StudioProjects/pinqdoq` (`git -C ~/StudioProjects/pinqdoq pull --ff-only` first) as the source of rules, references and scripts.
   3. Read **in full**: `rules/common.md` and every stack rule for the files you will touch (Kotlin: `kotlin-architecture.md`, `kotlin-naming.md`, `kotlin-conventions.md`, `kotlin-deveng-core.md` when deveng-core-kmp is a dependency; .NET: `dotnet-conventions.md`), plus the repo's own `CLAUDE.md`/`AGENTS.md`. Then read the deep references relevant to the change (`references/kotlin/*.md`, e.g. mvi-pattern, data-layer, viewmodel-patterns, error-handling, deveng-core-reference for UI).
   3a. **Our own libraries** (deveng-core-kmp, deveng-networking-kmp, pinqponq-chat-kmp, …) are local repos under `~/StudioProjects/<repo>`. To learn a component's API, read `references/kotlin/deveng-core-reference.md` first, then the library's source with `git -C ~/StudioProjects/<repo> fetch -q && git -C ~/StudioProjects/<repo> grep -n <Name> origin/<default-branch>` / `git show origin/<default-branch>:<path>` (never check out or edit the user's clone). Never unzip jars or read the Gradle cache for our own libraries (2026-10-07: a #401 run spent 3 calls unzipping the core jar for `CustomDialog`).
   4. Use the pinq-doq skills and their scripts for every step they cover (`pinq_add-feature` → `pinq_presentation-scaffold` / `pinq_api-endpoint-integration`, `pinq_kmp-theme-setup`); write code by hand only where no script applies, and say why in the PR.
   5. **Testing is part of the task, not an extra.** Read `rules/kotlin-testing.md` and `references/kotlin/testing.md` in full (merged in pinqponq/pinqdoq#19; if the repo's `.pinq-doq` submodule predates it, read them from `~/StudioProjects/pinqdoq` on `main`), plus the repo's CLAUDE.md "Testing" section, and apply Google's `testing-setup` skill principles (`~/.claude/skills/testing-setup`) as translated there. **Scope tests to the task — apply the MUST rules, not every SHOULD.** Every task adds/updates tests for the logic it changes (bug fix → a test that fails without the fix) and the UI behavior test for the interaction it changes. Screenshot tests only when the task changes how something looks, and only for the state it changes. Do **not** add extras the task does not need: large-font / `fontScale` variants, multiple window sizes, screenshots of unchanged components, test infrastructure or fakes for code the task does not touch. A SHOULD from `kotlin-testing.md` is added only when the task itself is about it (e.g. a new screen, an accessibility/font issue). 2026-10-01 incident: #377 (a delete race) added `preparing_dialog_*_large_font` and media-export screenshots; the team called them unnecessary scope. The PR lists the tests added and the exact commands run with their results.
   6. **Mutation testing is mandatory (PIT, diff-scoped).** After the tests pass and before `pinq_code-review`, run `python3 scripts/run_pit.py <worktree> origin/<default-branch>` (JVM/desktop tests; jars download to `~/.cache/pinq-pit` on first run; ~1 min). Rule text: `kotlin-testing.md` → "Tests must be able to fail". Score on changed lines must be **≥ 85%**; below it, add or sharpen tests for the survivors and rerun. Every remaining survivor goes into the PR's "Testler" section with a one-line reason (screenshot/device flow covers it, unreachable defensive path, equivalent/redundant code); a survivor on the core guard or branch the task introduces is never acceptable. A redundant call PIT exposes is removed or tested. Never widen the script's ignore list to raise the score. Repos whose tests are not JVM-runnable: say so in the PR instead of skipping silently. Rerun after every change request that touches tests or logic.
   7. **Test infrastructure:** rindle-cmp has it on `develop` (pinqponq/rindle-cmp#385). In a repo without test infrastructure, set it up first following `references/kotlin/testing.md` as its own PR and mention it in the run mail.
   8. **Comments follow `common.md` → "Comment Standards".** Default is no comment. Do not add KDoc/`/** */` or `//` comments that restate a name (e.g. a doc comment above a new `State` field like `isBulkDeleteProgressVisible`); before adding any comment, check whether the surrounding code has comments of that kind at all — if the file/feature has none, add none. A comment is allowed only for a verifiable business rule, external-system quirk, workaround (with tracking reference) or trade-off. 2026-10-01 incident: #377 added `/** A bulk delete is running; … */` above a State field; the team rejected it.
   9. **`pinq_code-review` runs on the whole branch, last, and its findings get fixed.** After all code for the run is done (including change requests), run `pinq_code-review` on the full diff `origin/<default-branch>...HEAD` — never only the last commit. Fix every Critical/Major **and every rule-backed Minor/Nit** in the changed lines (comments, naming, patterns); re-run until nothing rule-backed is left. Only findings outside the task's scope may stay, each listed with its reason. Put the final verdict (range reviewed, counts, what was fixed) in the PR under "pinq-doq uyumu".
4. Move the card to **In progress** with `python3 scripts/board.py move <task key> "In progress"` (never `gh project item-list`/`field-list`/`item-edit`, never hardcoded IDs), add the runner account as assignee (`gh issue edit <n> -R <repo> --add-assignee pinq-ponq`; existing assignees stay) and comment on the issue: `🤖 Bu task üzerinde çalışmaya başladım. Plan: …`.
5. **Code** following that repo's `CLAUDE.md` and `.claude/rules/` (for KMP repos: pinq-doq skills `pinq_add-feature`, `pinq_presentation-scaffold`, `pinq_api-endpoint-integration`). Stay inside the task's scope.
   **Follow existing patterns; never introduce a new structural one on your own.** Before writing a fix, find how the same kind of problem is already solved in the repo (`grep` for it) and do it the same way. Examples:
   - Error handling: errors are distinguished in the **ViewModel** via `launch(notifyError = false, onError = { exception -> if (exception.cause is DevengUiError.<Type>) … else setError(exception) })` (see `LoginViewModel`). Services stay thin calls to `devengNetworkingModule.sendRequest`; repositories and use cases stay pass-through.
   - Never bypass `DevengNetworkingModule` (raw Ktor `httpClient.delete/get`, `buildRequestUrl`, `setupAllHeaders`, hand-decoding `ErrorResponse`), never add new exception types or error-mapping layers in data/domain, never add a new base class, wrapper or helper that has no precedent.
   If the existing pattern cannot express what the task needs (e.g. the library maps the status you need to a generic error), **do not invent a workaround**: commit WIP, set `waiting_reply`, and ask (issue comment + mail, as in step 6) with options A/B/(C) and a recommendation — for example "A: ViewModel'de mevcut `DevengUiError` ile ayırt et (sınırlı), B: deveng-networking-kmp'ye 404 eşlemesi ekle (ayrı PR), C: ayırt etme, sadece çift isteği engelle". Any change with no precedent in the repo counts as a developer decision. 2026-10-01 incident: #377 replaced `sendRequest` with a raw Ktor call plus `GalleryMediaNotFoundException` in the service to detect 404; the team rejected it — the check belonged in the ViewModel, or should have been asked.
5a. **Backend parts are part of the task.** When the issue (or what the fix needs) includes backend work — an endpoint, status code, socket/push event, DB change — do it in the backend repo in the same run instead of listing it as "backend: needs human" (2026-10-02 incident: #380 left "4xx for match_already_matched + socket/push to the code owner on redeem" undone and only mentioned it in the mail; the team rejected that).
   - Repo: Rindle's backend is `pinqponq/rindle-backend` (.NET 10, C#). Locate/clone it like step 1 (`gh repo clone pinqponq/<repo> <workspace_dir>/pinqponq/<repo>` when no checkout exists) and work in its own worktree `<workspace_dir>/.task-runner-worktrees/<backend-repo>-<n>` on branch `task/<n>-<slug>` from `origin/develop`. Other products: find the backend in the org (`gh repo list pinqponq`) the same way.
   - Standards: the backend repo's `CLAUDE.md`, `docs/project-standarts.md`, `.claude/rules/common.md` + `dotnet-conventions.md`; follow existing patterns there exactly as step 5 says (same error-response shape, same response codes, same notification/socket mechanism already used for similar events). A schema/DB migration, a new service, auth changes or anything without precedent → ask by mail (A/B/C) before writing it.
   - Build and test: `export DOTNET_ROOT=/opt/homebrew/opt/dotnet/libexec`, `dotnet build` and `dotnet test` for the touched projects; add tests in the matching `*.Tests` project for every backend change. Run the same tests on `origin/develop` first and report only new failures as yours (on 2026-10-02 `RoutineServiceTests.LogRoutine_increments_count_and_creates_log` already failed on develop).
   - PR: ready-for-review PR (never draft) to `develop` with the same template, `Closes`/refs the same issue, and both PRs link each other ("Backend: pinqponq/rindle-backend#… — önce bu merge edilmeli"). Never push to `develop`/`master` (that deploys).
   - Device verification of backend-dependent behavior: api-test only runs what is merged to `develop`. Verify everything that works against the current api-test now; for the part that needs the new backend, add `backend_pr` and `pending_backend_verification: true` to the task, mail "backend PR merge edilince cihaz testi tamamlanacak", and on each later run check whether the backend PR is merged (`gh pr view`); once it is (and the deploy workflow finished), run the remaining Maestro scenario + pinqloq checks and update the mobile PR. Both PRs are opened ready for review right away; the mobile PR's "Notlar" says "rindle-backend#… merge edilmeden merge etmeyin; backend'e bağlı cihaz testi merge sonrası eklenecek".
   - deveng-core-kmp dependency (a Kotlin app task needing a core change, `blocked_by` a core task): do not wait for a core release. Once the core task's PR is open, build the app worktree against the core task's worktree with a local composite build in `settings.gradle.kts` (`includeBuild("<core worktree>") { dependencySubstitution { substitute(module("global.deveng:core-kmp")).using(project(":deveng-core")) } }`). That change is never committed: check `git diff --cached` before every commit and push. Set `core_pr` on the task; the app PR's "Notlar" says "deveng-core-kmp#… merge edilip yeni core sürümü yayınlanınca `global.deveng:core-kmp` bump gerekli; o zamana kadar CI derlemesi kırmızı olabilir". The user publishes the core version; on each later run check `gradle/libs.versions.toml` on the core repo's default branch / Maven Central for the new version and, once it exists, add the bump commit to the app branch and rerun the app tests.
6. **Questions mid-task:** if a decision appears that the issue/answers do not settle, commit WIP to the task branch, set `waiting_reply`, add the question (A/B/C + recommendation, numbered with `scripts/state_tx.py next-question`) to this run's mail **and** post it as a comment on the task's issue (`🤖 Soru S<n>: …`, with the options and how to answer: `S<n>: B`), since answers only arrive as issue comments; do not open a PR in this run (see "PR gate").
7. **Verify:** build and run the repo's tests (see its CLAUDE.md). For UI changes, run on the relevant targets and capture evidence into `media/<repo>-<n>/`:
   - **Test devices and accounts (login is never a blocker):** the runner signs in, signs out, unmatches and re-matches by itself. Saying "I can't log in" / "needs two unpaired accounts" and leaving the device test to a human is a runner error (2026-10-02: #380's pairing scenario was skipped this way; the team rejected it).
     - **Project specifics** (which test accounts exist and how to read them, account subflows, the state to restore afterwards, emulator snapshot and simulator setup, test-data rules): the project's `maestro/RUNNER.md` (rindle-cmp has one). Read it before the first device action. Test account values come only from `~/.claude/pinqloq-task-runner/test-accounts.json` at run time and go to Maestro only as `-e` env; never into the repo, PRs, mails, commits or logs.
     - If a device shows the login screen unexpectedly, sign in with `login.yaml` and continue; it is never a reason for `needs_human`.
   - **Order: pinqloq first, then Maestro.** Before any device run, check pinqloq for the affected flow **on the test environment only** — the test couple's userIds on api-test and your own earlier device runs (`get_error_summary` for `rindle_http` / `rindle_client` over the last 24h, plus `search_logs` for the endpoints/events the task touches). If it shows errors from the flow you changed, fix them (or record why they are unrelated) **before** spending time on device scenarios. Production only runs **released** code. A fix that is not merged and released cannot change production logs, so production errors continuing is expected until the release ships: never treat it as a finding, never report "the problem is still there in production" for an unreleased fix, and never use production as the baseline or the verification of a fix. Production logs are used only as the incident's context in "pinqloq: önce"; the fix is judged solely by the test-environment runs (develop build vs. task build). (2026-10-03: a #382 run checked production before release and reported the errors as still present; the owner pointed out that this is expected.) Only a clean or understood baseline moves on to Maestro. Note the UTC start time of each device run for the check afterwards.
   - **Device scenarios are Maestro flows** (`maestro/` in the repo, rules in `rules/kotlin-testing.md` "Proving UI changes on a device" and `references/kotlin/testing.md` § 8; rindle-cmp setup: pinqponq/rindle-cmp#389 — until it is merged, copy/run its `maestro/` from branch `chore/maestro-e2e`). Maestro is installed at `~/.maestro/bin/maestro` (`source ~/.zshrc`). Run with `maestro/scripts/run-flow.sh <android|ios> <flow>`; the same flow covers both platforms. Screenshots (`takeScreenshot`), recordings (`startRecording`/`stopRecording`) and the JUnit report land in `build/maestro/<platform>/`; use those as the PR's device evidence.
     1. **Reuse first:** list `maestro/**/*.yaml` and read the flows/subflows near the changed feature. Run or extend an existing flow when it covers the scenario; add steps to an existing subflow when a shared step is missing; write a new flow only for a scenario no flow covers. Say in the PR which flows were reused, extended or added.
     2. Explore a screen for selectors with `maestro --device <id> hierarchy` (slow, ~20–30 s — use it only while writing a flow, not to drive the test).
     3. Destructive flows seed their own data and act only on ids newer than one remembered before seeding (see `remember-newest-media-id` / `wait-for-seeded-media`); never widen that guard.
     4. A flow that fails is a finding: read the failing step's screenshot in `build/maestro/<platform>/…/screenshots/`, fix the flow or the app, and rerun. Don't fall back to hand-driving the device to get around a failing flow.
   - **Realistic scenarios — always test as close to reality as possible.** A device test proves the issue's scenario, not a convenient approximation of it.
     1. **Same actions, same order, same timing** as the issue/incident describes (e.g. "confirmed, then 4 s later pressed the trash icon again and confirmed again while the first delete was running" means exactly that sequence, not repeated taps on one dialog).
     2. **Same conditions:** data volume close to the incident (if 70 items made the delete take 8 s, reproduce a delete that takes seconds), realistic network (Android: `adb emu network delay <none|gprs|edge|umts>` / `adb emu network speed <…>` to widen race windows; reset to `none`/`full` afterwards; iOS has no easy throttle, so use more data or slower paths), the platform/build/locale of the report when it matters.
     3. **Prove the flow catches the problem:** run the same flow on a default-branch build first. It must fail, or produce the problem's footprint in pinqloq (e.g. duplicate `DELETE`s, 404s, client errors). If the old build passes cleanly, the flow is not realistic enough: revise it before testing the fix. That old-build run is the **"Önce"** of the before/after comparison (same conditions as "Sonra"); incident logs from production are added as context, not as the comparison baseline.
     4. Where exact reproduction is impossible or too costly, say so in the PR under **"Senaryo farkları"** (a table: reality vs. test, and how the condition was reproduced instead). Never present a happy-path run as proof that a race or edge case is fixed.
   - **iOS in unattended runs:** the Claude iOS Simulator control tool is **not available** in scheduled or reply-watcher sessions ("requires an attended session"). Do not try it and do not report it as a blocker — Maestro drives the simulator. The simulator has no camera: seed media through the app's import flow (Maestro drives the system photo picker; add files first with `xcrun simctl addmedia booted <file>` if the library is empty).
   - Hand-driving with `adb shell input` / `android screen capture --annotate` / `xcrun simctl io` is only for exploring a screen while writing a flow, never the verification itself.
   - Web: the built-in browser; screenshots via the browser tools. Compose/wasm web apps (pinqloq panel) first show a loading card that looks like a login form; wait until the real screen renders (`read_page`/`find` for an expected label, or a screenshot after a few seconds) before concluding anything. The panel keeps its sign-in in the built-in browser for `http://localhost:8080` (owner signed in there); reuse a dev server already listening on 8080 instead of starting a second one. Never type credentials. (2026-10-03: a #128 run took the loading card for a login screen and blocked the task.)
   - **pinqloq verification (mandatory for every task that runs on a device or touches app/backend behavior):** besides the baseline check before the device run (above), after each Maestro run confirm with pinqloq logs that the work did what it claims on the server/app side. Use the pinqloq MCP tools (`get_collections`, `search_logs`, `get_logs`, `get_error_summary`); they are often *deferred*, so load them with `ToolSearch` (query `pinqloq`) before concluding they are unavailable. Filter by the test couple's user and the scenario's time window, and check: the expected requests/events appear with the expected count (e.g. one delete request per item, no duplicates after rapid taps), and no new errors or exceptions come from the changed flow (`get_error_summary` before vs. after). Put the result into the PR template's pinqloq sections ("pinqloq: önce" / "pinqloq: sonra" for bugs, "pinqloq" for features) so a reviewer sees how the logs looked before the change and how they look after it:
     - **Önce:** the logs of the same Maestro flow run on a default-branch build (see "Realistic scenarios" step 3), so both sides share the same conditions. Add the real incident's footprint as context: search around the incident the issue cites (its timestamp, user, endpoint) and for the error event in history (`search_logs` over 30d). For a new feature, say what was absent before (e.g. endpoint never called) instead of inventing a "before".
     - **Sonra:** the **same queries** over each Maestro run window on the task build (Android and iOS separately).
     - Format: one small table per side (max 5 rows: request/event, status, count, time range) and the query in one line. No raw log dumps; at most one trimmed sample line when it is the only way to show the error. Redact device identifiers, emails, tokens and other personal data; a user id already given in the issue may stay.
     - `endTime` on `search_logs`/`get_logs` is not reliable (entries outside the window come back): query with `startTime` only and filter to the run window yourself.
     If pinqloq cannot be reached (tool missing, 401/auth error, timeout), do not substitute a unit test and call it verified: record the exact error, write `⚠️ pinqloq doğrulanamadı: <hata>` in the pinqloq section, set the task to `verification_blocked` (not done; do not open the PR yet — push the branch, and open the PR once pinqloq verification passes), and list it under "İnsan gerekiyor" in the run mail (once per day for the same error).

## No skipping without proof
The runner may not skip a required step on an assumption. In particular:
- **Device verification is mandatory for every UI-affecting task.** Boot the device, install the build, and run the issue's scenario as a Maestro flow on Android and (for shared UI) iOS. "No iOS tap tool" is not a blocker: Maestro drives the simulator. "Needs login", "needs another account", "needs unpairing" are never blockers: sign in/out, unmatch and re-match with the test accounts (step 7). "Needs data / needs a real device" may be claimed only after actually trying, and only with evidence attached (the screenshot of the blocking screen plus the command output). A blocker claimed without such evidence is a runner error.
- **Required tests are not optional.** If a MUST test from `kotlin-testing.md` looks hard (deep constructor graphs, concrete collaborators), creating the seam (an interface with a Default implementation, a fake, a test helper) is part of the task. Skipping is allowed only when the rule itself exempts the code, never because it is laborious.
- **pinqloq verification is not optional.** A task is not done until pinqloq logs confirm it (step 7) and the PR shows the before/after log comparison. A passing unit test, a screenshot, or "pinqloq was unreachable" is not a substitute; an unreachable pinqloq is reported as a blocker with the exact error, never silently skipped.
- **Code review covers the whole branch.** A review of only the last commit does not count; the PR's "pinq-doq uyumu" must name the reviewed range `origin/<default-branch>...HEAD`.
- **No unprecedented structure.** Before step 10, diff the change against `origin/<default-branch>` and list every new class, layer, library bypass or error-handling approach that has no existing counterpart in the repo; each one must either be removed (use the existing pattern) or have been approved by a mailed question. Say so in the PR under "pinq-doq uyumu".
- Before sending the run mail, self-check each task against this list; any unmet item keeps the task `in_progress` for the next run instead of being reported as done.
